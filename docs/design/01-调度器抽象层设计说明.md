# Lab3 调度器抽象层设计说明

## 1. 设计背景与原则

本设计基于 Lab3 实验指导书「**机制与策略分离**」的核心思想，在不修改内核调度机制层代码的前提下，将调度策略抽象为统一可插拔接口，实现 RR（轮转调度）与 MFQ（多级反馈队列）两种调度算法的无缝切换，同时明确团队分工边界，支持并行开发。

### 核心设计原则

1. **机制层零修改**：`scheduler()` 主循环、进程锁、状态机 re-check、`swtch` 上下文切换、页表切换等底层机制代码 100% 保留原生实现，不做任何改动。
2. **策略层可插拔**：所有调度策略逻辑封装在独立实现文件中，通过统一函数指针接口接入内核，新增调度算法无需修改机制层代码。
3. **基线可回归**：RR 调度器完全复现原生逻辑，任何时候切换回 RR 模式，系统行为与原版基线完全一致，可快速定位问题。
4. **编译期切换**：通过宏定义在编译期选择调度模式，无运行时额外开销，适合操作系统内核场景。

## 2. 整体架构

```
┌───────────────────────────────────────────────────┐
│           机制层（原生代码，零修改）                │
│  scheduler() 主循环 / 锁 / re-check / swtch       │
└─────────────────────┬─────────────────────────────┘
                      │ 统一策略入口
┌─────────────────────▼─────────────────────────────┐
│           调度器抽象层（sched_ops）                │
│  init / pick_next / enqueue / dequeue / time_tick │
└─────────┬───────────────────────────┬─────────────┘
          │                           │
┌─────────▼───────┐       ┌───────────▼───────────┐
│  RR 调度器实现    │       │  MFQ 调度器实现        │
│  sched_rr.c      │       │  sched_mfq.c          │
│  100%兼容基线     │       │  多级队列/升降级/老化  │
└─────────────────┘       └───────────────────────┘
```

上层机制层仅通过 `current_scheduler` 函数指针调用调度策略，完全不感知底层具体算法；新增调度算法只需实现 `sched_ops` 接口即可接入系统。

### 3.1 新增文件

表格

| `kernel/sched_mfq.c` | MFQ 多级反馈队列调度器占位实现，预留标准接口 |

### 3.2 修改文件

表格

| 文件路径 | 修改内容 |
| --- | --- |
| `kernel/proc.c` | 引入抽象头文件，新增调度器初始化函数，替换策略入口调用 |
| `kernel/trap.c` | 时钟中断接入 `time_tick` 统一接口，支持不同调度算法的滴答处理 |

| `Makefile` | 新增两个调度器实现文件的编译目标，加入内核链接 |

## 4. 核心接口定义

所有调度算法均实现 `struct sched_ops` 标准接口：

```
struct sched_ops {
    void (*init)(void);               // 系统启动时初始化一次
    struct proc* (*pick_next)(void);  // 选出下一个可运行进程（策略核心）
    void (*enqueue)(struct proc *p);  // 进程加入就绪队列
    void (*dequeue)(struct proc *p);  // 进程脱离就绪队列
    void (*time_tick)(void);          // 每个时钟滴答的处理（时间片、降级等）
};
```

### 接口语义说明

1. **init**：调度器初始化，负责就绪队列、全局变量、参数初始化，系统启动时调用一次。
2. **pick_next**：调度策略核心函数，对应原生 `pick_next_proc`，从就绪队列中选出下一个运行的进程。
3. **enqueue / dequeue**：进程状态变更时的队列操作，RR 模式无显式队列可空实现，MFQ 模式用于多级队列管理。
4. **time_tick**：时钟中断回调，RR 模式直接触发 yield，MFQ 模式可实现时间片计数、优先级降级等逻辑。

## 5. 模式切换机制

### 5.1 编译期切换

通过 `sched.h` 中的宏定义选择默认调度器：

```
#define DEFAULT_SCHED_MODE SCHED_MODE_RR   // 轮转调度
// #define DEFAULT_SCHED_MODE SCHED_MODE_MFQ // 多级反馈队列
```

修改宏后重新编译内核，即可切换调度模式，无需修改其他业务代码。

### 5.2 启动标识

内核启动时自动打印当前调度器类型：

```
[sched] Using scheduler: Round-Robin (RR)
[sched] Using scheduler: Multi-Level Feedback Queue (MFQ)
```

便于快速确认运行环境，方便后续对比实验与问题排查。

## 6. 团队协作边界

### 角色 A（架构负责人）

- 维护抽象层接口与机制层边界
- 保证 RR 模式基线兼容性
- 统筹联调与架构一致性

### 角色 B（MFQ 算法开发）

- 仅需修改 `kernel/sched_mfq.c`
- 按 `sched_ops` 接口实现多级队列、升降级、老化等算法逻辑
- 无需触碰 `proc.c`、`trap.c`、`main.c` 等机制层代码

### 角色 C（测试与统计）

- 可基于 `struct proc` 扩展统计字段
- 可通过封装调度接口加入埋点
- 基于双模式切换开展 RR vs MFQ 对照实验

## 7. 设计优势

1. **解耦清晰**：机制与策略彻底分离，算法迭代不影响内核核心稳定性。
2. **对比便捷**：同一套内核框架下，仅修改一个宏即可切换调度算法，便于性能对照实验。
3. **易于回归**：任何问题都可快速切回 RR 模式验证，排除架构改动引入的 bug。
4. **扩展性强**：后续新增其他调度算法（如优先级、CFS），只需新增一个实现文件，接入成本极低。
5. **分工友好**：团队成员可并行开发，互不阻塞，符合项目协作节奏。
